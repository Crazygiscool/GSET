# Python To Rust Plan

Status: **proposed** — Python Rust output is not yet implemented.
Decision date: 2026-11-03

GSET currently accepts Rust as a source language and emits the existing target set
(Go, Python, JavaScript, Java, Ruby). Python to Rust requires a new backend target
and remains experimental until its capability matrix is honest.

---

## 1. Goal

Make `gset transpile <project> --to rust` produce a Rust project that:

- builds with Cargo;
- runs for the supported Python subset;
- reports unsupported constructs as diagnostics instead of emitting
  confidently-wrong code;
- preserves project structure and dependency information in `gset.out`;
- passes generated tests where the source program exposes deterministic output.

The objective is to measure how far Python to Rust coverage can realistically
travel, not to claim support for dynamics that Rust cannot express directly.

## 2. Non-goals and explicit tradeoffs

- Arbitrary Python dynamic execution is not fully translatable to static Rust.
  Dynamic calls, runtime attribute addition, monkey-patching, and untyped
  global mutation remain experimental or unsupported unless tied to a specific
  API mapping.
- External Python packages are opaque by default. Rust has no `pygame`,
  `pandas`, or `requests` equivalent with the same API.
- Complete class semantics such as inheritance, multiple inheritance, runtime
  method insertion, and descriptors require a dedicated runtime model and should
  not be silently lowered to plain structs.
- Every unsupported feature must be reported. A translated corpus case is not
  claimed unless it passes `cargo check` or the relevant toolchain gate.

---

## 3. Capability boundaries

### Tier A: core portable subset

- integers, floating-point numbers, booleans, strings, `None`;
- assigned variables and inferred return types;
- arithmetic, comparisons, logical operators, and string building;
- function definitions, recursion, `if`, `while`, `for`, `break`, `continue`,
  and `return`;
- self-contained modules that print deterministic output.

### Tier B: project and data structures

- lists, dictionaries, sets, tuples, slices;
- classes with fields and methods;
- records and associated data carriers;
- keyword arguments and destructuring where they map safely to Rust syntax;
- exceptions, context managers, and pattern matching where typed encodings exist.

### Tier C: known semantic mismatches

- generators and lazy iteration;
- closures capturing mutable state;
- multiple assignment with runtime-dynamic types;
- comprehension laziness that is observable;
- truthiness over non-boolean values;
- late binding, duck typing, and reflection.

Tier C features should initially be marked `Support::Unsupported` or, if
desugared, carry compatibility warnings in the migration report.

---

## 4. Crate changes

### 4.1 Backend registration

- Add `TargetId::RUST` with name `rust`, extension `rs`, and a backend module at
  `crates/gset-backend/src/rust/mod.rs`.
- Register `Rust` in `backend_for()` and update `backend_by_name()`.
- Update extension and output handling used by the CLI.
- Add Python to Rust golden and corpus gate tests.
- Update `PipelineError` and naming output generated by the project pipeline to
  include Rust naturally instead of hardcoded Go/Python language names.

### 4.2 Rust emission strategy

The Rust backend follows the existing backend contract:

- implement `Backend::id`, `Backend::capability`, and `Backend::emit_module`;
- use the shared `CodeWriter`, with 4-space indentation;
- declare unsupported capabilities up front;
- report dropped/unsupported imports as `gset-backend-import`;
- report unexpressible constructs as `gset-backend-unsupported`.

Initial typing policy:

- explicit and inferred Python types map to Rust types directly:
  `int`, `float`, `bool`, `char`, `String`, `Vec<T>`, `HashMap<K, V>`;
- `Type::Unknown` maps to a selected representation chosen by the backend;
- functions infer `mut` parameters conservatively;
- functions default to `fn`, with `Result` reserved for functions that cannot be
  directly encoded;
- classes become structs with intrinsic methods before they become traits;
- imported names remain explicit and are diagnosed if no mapping exists.

### 4.3 Runtime model choice

Choose one of these before broad implementation:

- **Strict static model**: emit ordinary Rust types and mark dynamic Python
  constructs unsupported.
- **Dynamic value model**: introduce a supported runtime value type that can
  represent Python objects and preserve more behavior at the cost of heavier
  generated code.

Recommended default for initial work: strict static model first. The dynamic
model can later be introduced behind an optional experimental mode.

## 5. Dependency plan

Dependencies are classified in `gset-deps` as:

- `LocalPath`;
- `LockedRemote`;
- `Sdk`;
- `OpaqueForeign`.

Whole-library conversion behavior:

1. Source-available local and lock-file-verified dependencies are added to the
   project graph. If they are Python-only and no target mapping exists, they are
   copied as ported submodules when feasible, or emitted with todo markers when
   their constructs are not yet supported.
2. Runtime/SDK dependencies are emitted as passthrough imports and diagnostics.
3. Opaque foreign dependencies are reported with the target-side replacement
   or alternative required.
4. Unknown APIs remain diagnostics and handover items.

### Python library mapping registry

Create an explicit registry of Python modules and APIs mapped to Rust
dependencies and functions. Every mapping needs:

- source name;
- target crate or `std` module;
- alternative rust function or type;
- parameter count and admissible coercion rules;
- test coverage in the same commit;
- a confidence level: `guaranteed`, `experimental`, or `hint-only`.

Examples:

- `math.sqrt` -> `f64::sqrt`;
- `math.floor` -> Rust `math::floor` behavior;
- list slicing -> `Vec` range checks and helper function;
- exception handling -> `Result` only where mapped;
- `pygame` -> experimental mapping target candidates such as `macroquad`,
  `ggez`, or Raylib Rust, always emitted with adapter TODOs.

Unsupported dependencies should produce a migration entry rather than a silent
passthrough warning.

---

## 6. Project pipeline changes

Current project mode already provides:

- source discovery;
- module graph;
- local import resolution;
- external dependency classification;
- cache hashing;
- mirrored output.

Phase work required:

1. Generate a target project when requested. For Rust, emit a `Cargo.toml`
   alongside generated modules.
2. Preserve module names as Rust module paths.
3. Import graph edges should survive into generated `mod` declarations.
4. Dependency manifests should be hashed in the project cache.
5. Run `cargo check` and optionally `cargo test` after emission.
6. Keep generated file mode deterministic and relative to source roots.

---

## 7. Whole-library non-goals for first milestone

The first Rust backend milestone should not promise arbitrary third-party
libraries. It should support representative small programs and standard-library
patterns, while marking all external packages as handover tasks.

Examples of demonstrated coverage:

- `fib.py` builds and outputs `55`;
- self-contained numeric fixtures execute identically before and after
  translation, where supported;
- unsupported constructs are reported with `gset-backend-unsupported`;
- project mode emits diagnostics for `numpy`, `requests`, or `pygame` rather
  than pretending source transpilation exists;
- each corpus case has an `ok`, `backend`, `frontend`, `malformed`, or `invalid`
  state and the Rust baseline is checked in.

---

## 8. API mapping experimental mode

Recommended mode boundary:

- default mode: hint-only and passthrough;
- `--api-map experimental`: apply registered translations;
- only mappings with at least one test fixture and a runnable comparison may be
  used;
- generated code must include comments or diagnostics identifying every
  experimental substitution;
- translation failures revert to hint-only behavior for that program rather
  than aborting when possible.

Every mapping should be scoped to a function or module before broader support.
This avoids pretending that a method like `requests.get` or `pygame.draw.rect`
is semantically replaceable without a target package and adapter layer.

---

## 9. Implementation milestones

### Milestone R0: target registration

- Add Rust target identity and backend module.
- Emit simplistic valid Rust for a minimal `main` and function.
- Add CLI and gate infrastructure.

### Milestone R1: core Python subset

- arithmetic, variables, typed expressions, calls;
- `if`, `while`, `for`, return;
- deterministic Python to Rust test fixture;
- report generators, async, decorators, and context managers.

### Milestone R2: project and data

- lists, dictionaries, strings, slices;
- functions with inferred returns;
- struct records and method calls;
- project-mode Rust crate layout;
- dependency classifications in diagnostics.

### Milestone R3: API and library support

- standard library API mapping registry;
- whole dependency graph traversal;
- migration report with alternative target libraries;
- experimental API-level translation available behind a flag;
- runtime tests for generated Rust programs.

### Milestone R4: coverage expansion

- closures, classes, exceptions, traits;
- iterators and comprehensions where safe;
- compile and integration gates on all corpus features;
- honest baseline and diagnostics.

Assumption: no commit claims production coverage until the associated generated
program builds and runs or is explicitly classified as a documented gap.

---

## 10. Verification

Required commands, adapted for the toolchain:

- `cargo build --workspace --all-targets`
- `cargo test --workspace`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo fmt --all -- --check`
- `cargo deny check`
- `cargo test -p gset-cli --test corpus_rust_gate`
- generated Rust programs must pass `cargo check` and `cargo test` as applicable

Rust tools should be treated as required CI provisions for the Rust target.
Machine tooling that appears missing must skip rather than fail only for optional
gate layers; core compiler checks required by this plan should not be skipped.

---

## 11. Recommended defaults

1. Focus Python to Rust first, rather than broad cross-language breadth.
2. Make generated Rust compile/run with `std` and explicit helpers.
3. Treat stdlib imports as mappings, not source transpilation.
4. Make all third-party library calls tagged hints until a checked registry
   advertises stable support.
5. Keep `--api-map` explicitly experimental until generated tests prove both
   compilation and matching behavior.
6. Treat unsupported source features as diagnostics and gate regressions.
7. Add a migration report so users can see which constructs and dependencies
   require manual work.
8. Use this plan as the source of truth for Python to Rust capability claims.
